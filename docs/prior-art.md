# Prior art (checked 2026-11-01)

This note credits the open projects that tackle the same problem, and says plainly what this one uses and what it only has in common with them.

Stars and last push date are as GitHub showed them on 2026-11-01. The licence is taken from the repo's licence file. Where there is no file, the note says where the licence is stated, or "no licence file".

Per its [LICENSE](https://github.com/esphome/esphome/blob/dev/LICENSE), the C++ runtime is GPLv3 and the Python side is MIT, so a compiled firmware image contains GPLv3 code. Components used:
  - [`pid` climate](https://esphome.io/components/climate/pid/), including its relay autotune (`climate.pid.autotune`), `max_integral` and output averaging. The values in use are hand-tuned.

  - [`slow_pwm`](https://esphome.io/components/output/slow_pwm/) to time-proportion the SSR.
  - [`rotary_encoder`](https://esphome.io/components/sensor/rotary_encoder/) for the EC11 dial (the push is a GPIO binary sensor).
  - [`ssd1306_spi`](https://esphome.io/components/display/ssd1306/) with model `SH1107 128x128` for the 1.12" OLED, and [`font`](https://esphome.io/components/font/) with Roboto Condensed pulled through `gfonts://`.
  - Template switches, numbers and buttons, `globals`, `script` and `interval` for the session, the faults and the Soaking state.
- **Home Assistant** ([home-assistant/core](https://github.com/home-assistant/core), Apache-2.0): the [ESPHome integration](https://www.home-assistant.io/integrations/esphome/), [packages](https://www.home-assistant.io/docs/configuration/packages/), [scripts](https://www.home-assistant.io/integrations/script/) for sessions and the ramp, a trigger-based [template sensor](https://www.home-assistant.io/integrations/template/) for the pull counter, the [history graph card](https://www.home-assistant.io/dashboards/history-graph/), and [companion app notifications](https://companion.home-assistant.io/docs/notifications/notifications-basic/).

## Similar work and ideas we share

These are parallel projects found while writing this note. No code from any of them is in this repo. The firmware is ESPHome config, and the HA side is HA YAML written for this box. Nothing found while checking these repos suggests otherwise. Where the ideas match, it is because the problems match:

- **Soak before Ready ↔ reflow soak and heat soak.** Rocket Scream's soak phase, hardboiledfrog's insert heat soak and CleverCoffee's "wait for the group head" all give the heat time to reach the part that matters. T-962's bake timer waits for the set point the same way. Gaggiuino's "soak" is a different thing with the same name.
- **Ramp session ↔ reflow profiles and kiln schedules.** Rocket Scream steps its set point on a timer, and esphome-kiln-api runs ramp/target/hold steps. fc-enail scripts and the Dr Dabber "Ascent" mode do the same for e-nails. Our ramp waits for Ready before climbing, like jbruce12000's `kiln_must_catch_up` and fc-enail's wait-for-set-point step.
- **Pull counter ↔ espresso shot detection.** CleverCoffee v3.x software brew detection uses almost the same rule: a fast temperature fall while near the set point, then re-arm. hardboiledfrog counts whole cycles, and the Dr Dabber integration reports heating cycles per day.
- **Master relay ↔ second cut-off.** PIDKiln adds a mechanical relay in series with the SSR for exactly our reason: SSRs can fail closed. jbruce12000 alerts on a relay stuck on.
- **"No heat" fault ↔ thermal-runaway checks.** IronOS, PIDKiln (`Thermal_Runaway`) and jbruce12000 (`emergency_heat_rate`) each stop when the heater runs but the temperature doesn't rise.
- **Probe fault ↔ thermocouple error states.** Rocket Scream has an error state, octo-nail skips NaN readings and hardboiledfrog ignores readings of 0 or below. CleverCoffee flags a sensor after repeated bad reads.
- **Max session time ↔ auto-off.** AerPID3's auto-off, hardboiledfrog's cycle run time and CleverCoffee's standby timer.
- **Dial + small screen.** hardboiledfrog, octo-nail, Another-HotPlate-Firmware, fc-enail, AerPID3 and PIDKiln all use a rotary encoder with a push as the main control.

## Ideas worth borrowing later

- **Stuck-SSR check.** If the coil keeps rising while the PID output is 0, open the master relay and show a fault. From jbruce12000/kiln-controller's `relay_stuck_on` alert ([`config.py`](https://github.com/jbruce12000/kiln-controller/blob/main/config.py#L259-L270)).
- **Run the ramp on the device.** Then it keeps going if HA or Wi-Fi drops, instead of holding the last target. From kiln-controller/esphome-kiln-api's on-device schedule ([`kiln_api.h`](https://github.com/kiln-controller/esphome-kiln-api/blob/main/components/kiln_api/kiln_api.h#L49-L54)).
- **Recovery PID after a pull.** Switch to a stronger PID set for a few seconds after a detected pull, then switch back. From CleverCoffee's brew-detection PID ([v3.1.0](https://github.com/rancilio-pid/clevercoffee/blob/v3.1.0/src/rancilio-pid.cpp#L837-L849)).
- **Bump.** A short, capped "+N degrees for M seconds" from the dial. From AerPID3's bump ([`elementTask.h`](https://github.com/Aerify-Digital/AerPID3/blob/master/src/tasks/elementTask.h#L22-L60)) and IronOS's boost mode.
- **Multi-point curves.** Allow 2–6 temperature/time points instead of only From → To. From the Dr Dabber integration's `set_curve` service ([README](https://github.com/edweiss412/ha-drdabber-switch2/blob/main/custom_components/drdabber_switch2/README.md)) and T-962's editable profiles.
- **A second probe for the box.** Use a cheap sensor on the SSR heatsink or inside the case, with its own cut-off. From PIDKiln's housing probe ([`pidkiln.conf`](https://github.com/Saur0o0n/PIDKiln/blob/master/data/etc/pidkiln.conf#L85-L89)).
